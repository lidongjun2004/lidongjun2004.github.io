## 1. 为什么需要知识图谱

### 1.1 信号 → 数据 → 信息 → 知识（4 层概念，期末辨析题常考）

| 层级 | 是什么 | 例子 |
|---|---|---|
| **信号** | 传感器测量的物理量，信息的物理载体 | 电流、电压、温度 |
| **数据** | 信号被存储/显示出来的内容 | 文本"226"、连续温度值 |
| **信息** | 数据 + 解释，带语义 | "姚明身高 2.26 米" → "姚明很高" |
| **知识** | 被验证、正确、被相信的有价值信息 | "中国的首都是北京" |

**关键区分**：
- 数据 = 字面量；
- 信息 = 理解后的数据；
- 知识 = 验证过的信息。

### 1.2 感知智能 vs 认知智能

- **深度学习**擅长"感知"（看、听、识别）；
- **知识**是"认知"（理解、推理、决策）的燃料；
- 例："特朗普住哪？"——纯 DL 答不出；引入"美国总统住白宫"这条常识即可推理。

### 1.3 知识驱动 vs 数据驱动

| 维度 | 知识驱动 | 数据驱动 |
|---|---|---|
| 依赖 | 预定义规则和逻辑 | 从数据中学模式 |
| 擅长 | 结构化、定义明确的任务 | 复杂、非结构化任务 |
| 代表 | 专家系统、规则系统、KG | 深度学习、大模型 |

> 大模型幻觉的根因之一是知识不全/不准；KG 给机器外挂结构化、可推理的知识库。

## 2. 知识图谱的定义

> **知识图谱**是一种用有向图模型来描述知识和建模世界万物之间的关联关系的技术方法，由**节点**和**边**组成。

- 2012 年 Google 在搜索引擎中首次提出"Knowledge Graph"；
- 以图数据结构描述概念、实体及其关系，**更接近人类认知形式**。

## 3. 基本概念

### 3.1 三元组（KG 最基本单位）

**关系事实 = (头实体, 关系/属性, 尾实体)** = RDF 三元组 = SPO 三元组。

- 头实体 = Subject
- 关系/属性 = Predicate
- 尾实体 = Object

例：
```
(北京航空航天大学, 成立于, 1952年)
(北京航空航天大学, 教职工人数, 4266)
(北京航空航天大学, 学生人数, 37000)
```

### 3.2 两层结构（最重要的一张图）

| 层 | 内容 | 作用 | 例子 |
|---|---|---|---|
| **概念层 / 模式层** | 抽象的"类"、本体、本体间关系 | KG 骨架，约束实例 | 体育人物、娱乐人物、城市 |
| **实例层 / 数据层** | 真实实体 + 实体间关系 | KG 血肉，存事实 | 姚明、韩寒、上海 |

**连接关系**：
- 概念层之间用 **Subclass**（体育人物 Subclass 人物）；
- 概念↔实例用 **Instance Of / Type**（姚明 Type 体育人物）；
- 实例之间用 **Relation**（姚明 出生于 上海）。

**为什么要分两层**：
1. 概念层约束实例层，防"姚明属于水果"；
2. 支持基于概念的推理（"体育人物会打篮球" → "姚明会打篮球"）；
3. 本体可独立复用和扩展。

### 3.3 节点的层次化表示

```
领域（Domain/Topic）    人物、自然、文化…
   └─ 概念（Concept）   体育人物、娱乐人物…
        └─ 实体（Entity/Instance）   姚明、韩寒…
```

### 3.4 节点类型

| 类型 | 含义 | 例子 |
|---|---|---|
| **实例（Instance）** | 真实实体 | （姚明，出生地，上海市） |
| **字符串（String）** | 文本值 | （北京大学，学术传统，兼容并包、思想自由） |
| **数值（Number）** | 数字 | （北京市，面积，1.641万）、（姚明，身高，2.29米） |
| **时间（Date）** | 日期 | （姚明，出生年份，1981年） |

### 3.5 边类型

| 类型 | 连接什么 | 例子 |
|---|---|---|
| **Subclass（子类）** | 本体之间 | （体育人物，Subclass，人物） |
| **Type（类型）** | 实体 ↔ 本体 | （姚明，Type，体育人物） |
| **Relation（关系）** | 实体之间 | （姚明，出生于，上海）、（姚明，朋友，奥尼尔） |

> 属性 vs 关系：属性图里都叫"边"；RDF 里属性要加一个特殊节点表示。

## 4. 发展历史（5 个里程碑）

| 阶段 | 时间 | 核心 | 关键人物/事件 |
|---|---|---|---|
| **专家系统（ES）** | 1970s | 知识库 + 推理机，人工写规则 | MYCIN（医疗） |
| **本体（Ontology）** | — | 结构化术语集，概念间关系 | 哲学起源 → AI |
| **万维网（WWW）** | 1989 | 文档靠超链接互联 | Tim Berners-Lee |
| **语义网（Semantic Web）** | 2001 W3C | 给网页加机器可读语义 | W3C |
| **链接数据（Linked Data）** | — | URI 标识万物 + RDF 互联 | 语义网落地 |
| **知识图谱** | 2012~ | Google 正式命名 KG | YAGO/DBpedia/Wikidata 等百花齐放 |

### 知识工程 vs 知识图谱（要背）

| 维度 | 知识工程 | 知识图谱 |
|---|---|---|
| 构建 | 人工 | 自动 + 众包 |
| 数据量 | 万~十万 | 数十亿~数万亿三元组 |
| 表示 | 一阶逻辑/产生式/描述逻辑 | RDF/属性图/分布式表示 |
| 任务 | 逻辑推理 | 检索 + 推理，赋能搜索/问答/推荐 |

### KG vs 传统知识库 vs 数据库

| 类型 | 主要任务 | 备注 |
|---|---|---|
| 数据库 | 数据处理 | 表结构、强 schema |
| 传统知识库 | 知识处理 | 重推理、量小 |
| 知识图谱 | 知识应用 | 量大、含语义、可推理、形式灵活 |

> KG 不替代数据库，KG 是更高层的语义层。

## 5. 典型知识图谱（期末选择题重灾区）

### 5.1 通用 KG vs 领域 KG

| 维度 | 通用 KG | 领域 KG |
|---|---|---|
| 知识来源 | Wikipedia/众包 | 行业/企业内部数据 |
| 规模化 | 渐进 | 快速大规模 |
| 表示 | 三元组事实型 | 复杂本体 + 规则 |
| 质量 | 开放域 + 容忍度 | 抽+人工审核、质量高 |
| 融合 | 提升质量 | 多源融合扩展 |
| 应用 | 搜索/问答 | 决策/业务管理（**重推理**） |
| 举例 | DBpedia、Yago、百度、谷歌 | 电商、医疗、金融、农业、安全 |

> 互补：通用提供基础 → 行业复用+加深 → 回流补充通用。

## 6. 技术流程（4 个关键问题）

### 6.1 整体架构

```
应用层    语义搜索 / 智能问答 / 辅助决策
服务层    知识存储 / 知识检索 / 知识推理
支撑层    NLP / 知识抽取 / 知识表示 / ML / DL / 图数据库
         知识融合 / 知识众包 / 知识建模 / 大模型
数据层    非结构化 / 半结构 / 结构化 / 多媒体结构 / 众包
```

### 6.2 四个关键问题（4 个动词）

| 关键问题 | 解决什么 | 主流方法 |
|---|---|---|
| **知识表示** | 知识怎么"写"成机器能懂的符号 | RDF / 属性图 / OWL / 表示学习 |
| **知识抽取** | 怎么从数据里把知识挖出来 | 实体识别 / 关系抽取 / 事件抽取 |
| **知识融合** | 多源 KG 怎么合并成一个 | 实体对齐 / 消歧 / 共指 |
| **知识服务** | 怎么用知识 | 补全 / 推理 / 语义检索 / 问答 |

### 6.3 4 个问题展开

**① 知识表示**
- 本体：类集、属性集、关系集、词汇集；
- 实体：实体间关系 + 描述术语；
- 事件：实体关联 + 发生时间；
- 基本描述框架：W3C 的 RDF = 主谓宾三元组。

**② 知识抽取**
- 结构化数据 → D2R 工具：Triplify、D2RServer、OpenLink、SparqlMap、Ontop；
- 文本数据 → 实体识别 + 关系抽取；
- 关系抽取方法演进：**特征模板 → 核函数监督 → 远程监督 → 联合抽取 → LLM**。

**③ 知识融合**
- 模式层：新本体融入已有本体；
- 数据层：实体指称、属性、关系、类别融合；
  - **实体消歧**：同名实体不同含义（"苹果"公司 vs 水果）；
  - **共指消解**：不同命名指同一实体（"北航" = "北京航空航天大学"）。

**④ 知识服务**
- **本体推理**：基于描述逻辑，对概念/关系补全；
  - 例：`(X,出生于,Y) ∧ (Y,属于国家,Z) ⇒ (X,国籍,Z)`；
  - 事实：姚明出生于上海 + 上海属于国家中国 → 推出姚明国籍中国。
- **图结构推理**：实体间路径 + 周围图结构预测关系；
- **表示学习推理**：实体/关系嵌成向量，h + r ≈ t（TransE）；
- **知识检索**：语义搜索，给出精确答案 + 相关推荐；
- **辅助决策**：KG 嵌入分析/推荐流程。

### 6.4 知识存储两条路线

- **三元组库**（Semantic Web 出身）：存 RDF，代表 Apache Jena、OpenLink Virtuoso；
- **图数据库**（数据库出身）：存属性图，代表 **Neo4j**、JanusGraph、OrientDB；
- **核心区别**：RDF 边/点无属性，要加属性得新加节点；属性图原生支持键值对属性。

## 8. 课件补全与勘误

### 8.0 从第四范式理解课程开场

课件先用 Jim Gray 所说的“第四范式”交代背景：科学研究从实验观察、理论建模、计算仿真，进一步走向从海量数据中分析和挖掘新发现。数据驱动的深度学习和预训练模型因此很强，但模型准确性依赖训练数据能否充分覆盖目标场景。

知识图谱补的是另一侧：把交通规则、事实关系等可复用知识显式组织起来，使系统不只做感知模式匹配，还能依据知识推理和决策。它与数据学习不是互斥路线，而是“训练中学到的统计模式”与“可查询、可解释的结构化知识”互补。

### 8.1 两层结构要把“约束”与“事实”连起来看

![知识图谱的概念层与实例层](/images/knowledge-graph/kg-two-layer-structure.png)

*概念层规定有哪些类和关系，实例层保存具体实体与事实；`type` 把两层连起来。*

模式层并不是摆在数据上方的一张分类表，而是实例事实的语义合同。例如，模式层先声明“体育人物”是“人物”的子类、`出生于` 的两端应当是“人物”和“地点”，实例层再保存“姚明出生于上海”。这样既能检查数据类型，也能沿 `subClassOf` 和 `type` 做继承推理。

> **数值勘误**：前文节点类型表中的“姚明身高 2.29 米”与课件不一致。课件从“数据—信息—知识”的例子到两层结构图都使用 **2.26 米**，复习和答题应以 2.26 米为准。

### 8.2 发展线与规模口径

前文标题写“5 个里程碑”，但表格实际有六个阶段。按课件时间轴应记为：

$$
\text{专家系统（1970s）}
\rightarrow \text{本体（1980）}
\rightarrow \text{WWW（1989）}
\rightarrow \text{语义网（1998）}
\rightarrow \text{链接数据（2006）}
\rightarrow \text{知识图谱（2012）}.
$$

课件对规模的对照是：传统知识工程的知识库常在**数万到数十万**量级，知识图谱通过机器学习、自然语言处理等方式自动化构建，数据量可到**数十亿至数百亿**量级。前文“数十亿到数万亿三元组”可用来理解更广泛系统的可能规模，但不是这页课件给出的比较口径。

时间轴把语义网节点标在 1998 年，而正文又说 W3C 在 2001 年开始建立语义网技术规范；这是课件呈现的两个口径。复习时保留二者即可：前者是演化图上的阶段标记，后者是正文对 W3C 推进工作的叙述。

### 8.3 搜索、问答、推荐到底改变了什么

| 应用 | 没有 KG 时 | 引入 KG 后 |
|---|---|---|
| 搜索 | 关键词匹配并返回网页 | 对人物、机构、地点等“事物”直接索引，返回精确答案和相关内容 |
| 问答 | 从文档中检索可能相关的片段 | 把问题链接到实体和关系，沿图查询或推理后给出更精准的答案 |
| 推荐 | 主要利用用户—物品共现，理由不透明 | 沿演员、导演、类型等关系找候选，兼顾精确性、多样性与可解释性 |

推荐例子的关键不是“知识图谱取代协同过滤”，而是它提供了一条能说清楚的路径：用户看过多部沈腾主演的电影，所以推荐同样由沈腾主演的《飞驰人生》。实际系统通常会把图特征与协同过滤、排序模型结合。

### 8.4 菜谱领域知识图谱：四步闭环

![领域知识图谱的技术流程](/images/knowledge-graph/kg-technical-pipeline.png)

*先定义语义，再抽取事实、融合指称，最后用存储和推理引擎对外服务。*

1. **知识表示**：输入“饮食”领域和问答、检索等应用场景，输出菜谱本体，包括食材、菜品、步骤等类别及属性、关系。
2. **知识抽取**：从结构化、半结构化和非结构化数据中抽出实体、关系与属性，如“水煮肉片—包含食材—花椒”。
3. **知识融合**：结合本体和现有知识库，对齐“土豆—马铃薯—洋芋”“西红柿—番茄”等不同指称，形成统一图谱。
4. **存储、查询与推理**：把融合后的知识交给存储、检索和推理引擎，通过 SPARQL 等接口回答“酸辣土豆丝需要花椒吗”“水煮肉片怎么做”。

这四步不是一次性流水线。发现新数据或本体不够用时，需要回到表示、抽取和融合阶段继续迭代。

课件还给了一个最小推理例子：北航有 4266 名教职工、37000 名学生，并给出“学校总人数 = 教职工人数 + 学生人数”的规则，于是可算得

$$
4266+37000=41266.
$$

三元组负责存事实，规则负责把事实组合成新结论，这正是“知识 + 推理”的最小闭环。

### 8.5 存储路线的准确边界

- **RDF 三元组库**围绕 RDF 图与 SPARQL 标准展开，适合关系语义、数据交换和本体推理。课件列举 RDF4J、RDF-3X、gStore 与 Virtuoso。
- **属性图数据库**让节点和边原生携带键值属性，适合遍历和工程业务查询。课件列举 Neo4j、JanusGraph 与 OrientDB，查询语言可用 Cypher、PGQL 等。
- 前文“RDF 边/点无属性”说的是它与属性图的**原生数据模型差异**，不等于 RDF 永远不能描述“这条陈述的时间、来源或置信度”。RDF 可借助具体化（reification）、命名图或 RDF-star 一类机制表达陈述元数据，只是建模方式不同。
- 所以 KG 并不替代数据库：图模型规定如何组织语义，数据库系统仍负责索引、持久化、并发和查询执行。

### 8.6 课件思考题

1. ChatGPT、搜索引擎和知识图谱分别擅长什么，三者怎样协作？
2. 怎样构建类似“活词典”的知识图谱，让机器读懂教科书、跨网页查找并组合答案？
3. 面对开放世界，怎样表示动态变化、不确定性和复杂事件，并完成可靠推理？
4. 怎样连接知识图谱的符号空间与深度学习的向量空间，并进一步处理多模态知识？

可以把四题串成同一条主线：**知识从哪里来，如何保持正确，怎样参与计算，最后如何服务真实问题。**
